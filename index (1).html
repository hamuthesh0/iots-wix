01 / Problem Statement

The wait doesn't end at the consultation room door.

A Parliamentary Question and Answering response published by the Ministry of Health Singapore found that the overall median doctor consultation waiting time for walk-in patients at polyclinics in February 2023 was 17 minutes — and that figure doesn't include the wait to collect medication afterwards.

After a consultation ends, patients face an additional wait for medication collection, compounding the strain on their time and attention. There is a clear need for a secure IoT-enabled medication locker that reduces collection wait time, ensures patients receive the correct prescribed medication, and reduces manpower strain through automatic refill notifications and continuous monitoring of medication storage conditions.

Guiding Question How can we streamline the medication prescribed process in hospitals?
02 / Introduction

An edge device that locks, senses, and reports — all at once.

The proposed system is a secure medication collection locker built around an ESP32, keypad, DHT22 sensor, ultrasonic sensor, servo motor, and buzzer — networked and integrated with cloud systems.

The ESP32 acts as an IoT edge device, collecting and processing data and controlling actuators to carry out required actions. Sensor readings are transmitted to ThingSpeak for cloud visualization, while a web application and database manage patients, prescriptions, inventory, and access records. Security controls are applied across the device, network, application, and database layers to protect the system from unauthorized medication collection and data exposure.

IoT systems are increasingly used in real-world scenarios to improve operational efficiency and convenience, yet publicly available information rarely details their IoT architecture, environmental monitoring, or security event logging. This project focuses on demonstrating those technical and cybersecurity features using an ESP32-based locker, cloud monitoring, and role-based access control.

03 / Literature Review

Two frameworks shaped every technical decision.

IoT platform requirements

Mineraud et al. (2015) reviewed a range of IoT platforms and identified core platform functions: device management, communication support, data processing, data storage, application development, and security. An effective platform supports communication between sensors and actuators while allowing collected data to be processed and accessed by applications.

In MediSync, the ESP32 performs device control and edge processing; ThingSpeak stores and visualizes temperature and humidity readings; the backend and MongoDB database manage users, prescriptions, inventory, locker assignments, and audit records. Separating these concerns improves modularity — changes to sensor monitoring don't require changes to the patient or staff application — while dedicated security controls close the privacy and security gaps identified in existing IoT platforms.

IoT architecture and technology landscape

The IDA IoT Technology Landscape describes an IoT system as a stack of connected layers: sensors and actuators, local communication networks, gateways, wide-area communication, service platforms, and user applications. In MediSync, sensors such as the DHT22 and ultrasonic sensor collect data from the physical environment, while actuators — the servo motor, buzzer, LED, and LCD — carry out commands from the ESP32. Gateways connect local devices to external networks, and the cloud platform provides data storage, analysis, device management, and application support.

Synthesis

Together, the two sources shaped the system end to end: the IDA landscape organizes the project into device, edge, network, cloud, and application layers, while Mineraud et al. (2015) surfaced the platform capabilities and security concerns — device management, communication, data processing, interoperability, privacy, and secure application access — that guided the choice of ESP32, ThingSpeak, MongoDB, the web application, and the system's security controls.

05 / Our Solution

From counter hand-off to a secure, automated pickup.

MediSync is an IoT-enabled self-collection locker for medicine that transitions traditional counter collection into a secure, automated process.

When a patient's appointment ends, the attending doctor electronically transmits the prescription to the system. The system instantly updates the inventory database, deducts stock, and issues a unique authentication method to the patient, who uses it to securely unlock and retrieve their medicine at a self-collection kiosk. Once marked as collected, that authentication method is immediately retired — it cannot be reused.

To keep operations running, the system continuously monitors storage temperature, triggering an alarm on fluctuation, and automatically alerts nursing staff to restock using secure credentials when inventory runs low. Temperature and humidity readings from the DHT22 sensors flow to ThingSpeak and display on cloud dashboards, so medication condition is always visible.

06 / Proof of Concept Design

Hardware and physical security, working together.

An all-day medicine pickup station made possible by hardware working seamlessly together — showing how digital systems handshake with physical infrastructure to automate dispensing.

Hardware

  • TouchscreenLets patients enter verification details or sign in for collection.
  • Camera / QRReads electronic tokens from a mobile health app or printed prescription.
  • Smart locksSolenoid lock actuator per compartment, linked to the central unit.
  • DHT sensorsMonitor temperature for temperature-sensitive medication.
  • IoT / networkingRouters and cellular modems link lockers to the pharmacy database and SMS gateway.
  • CCTVContinuous surveillance of the collection station.

Physical & access security

  • Ruggedized, tamper-resistant steel locker panels
  • Overhead CCTV recording the station 24/7
  • Internal solenoid latches — no external handles or keyholes to pry open
  • Singpass integration for national identity verification
  • Two-factor / dynamic OTP required before unlock
  • Appointed collection tracking with a digital audit trail
  • 48-hour pickup window, then key wipe and staff-only retrieval
07 / System Architecture

Edge to cloud, in one continuous loop.

The ESP32 sits at the edge, interfacing directly with sensors — the DHT22 collects temperature and humidity, while the keypad and servo motor form the authentication and physical door lock. The ESP32 communicates with the cloud; ThingSpeak receives readings for visualization, and the cloud backend processes access-control decisions and maintains collection and security records.

Flowchart

The patient books an appointment through the hospital's website; a one-time OTP is sent for verification, followed by a confirmation email. After the appointment, the doctor keys in the required medicine via a website connected to MongoDB — transferred over HTTPS and TLS. Inside the locker, a DHT sensor constantly monitors temperature and humidity, and an ultrasonic sensor checks whether the door is closed. The patient receives a password to collect medicine, enters it on the keypad as prompted by the LCD, and the servo motor dispenses the medicine.

10 / Security Design Using TR64

Twenty-one controls, mapped requirement by requirement.

Every TR64 IoT Security Standard requirement below is matched to the specific mechanism in MediSync that satisfies it.

Req. IDTR64 RequirementHow the Project Complies
CS-02Cryptographic algorithms should be industry recognised and deemed secure.Secure cryptographic algorithms (e.g., HTTPS/TLS) protect communication between the website, NodeMCU, and MongoDB database.
CS-03AES should be used for symmetric cryptography.Patient data, PINs, and medicine records stored in the database are encrypted using AES to ensure confidentiality.
CS-05Proper key management should be established.Encryption keys and authentication credentials are securely managed server-side and never exposed to users or IoT devices.
IA-01Credentials should be stored securely.Patient PINs, doctor login credentials, and nurse RFID information are stored using hashing or encryption.
IA-02Client should be authenticated before establishing connections.Patients enter the correct PIN (optionally with facial verification); nurses authenticate via RFID before accessing the locker.
IA-03Unique, non-modifiable and verifiable identities should be established.Every patient, doctor, and staff member has a unique identifier verifiable by the system.
NP-01Explicit authorisation should be required for an initial connection.Only NodeMCU and the registered web server are allowed to communicate with the system.
NP-03Proven transport protocols with TLS/DTLS should be employed.Communication between the web app, cloud database, and NodeMCU uses HTTPS/TLS.
NP-06Network access control may be implemented.Only authenticated users and trusted devices may access the IoT network and medicine management system.
FP-01Security credentials, keys and tokens should be protected.PINs, RFID credentials, authentication tokens, and encryption keys are protected from unauthorised access.
FP-02Integrity of security functions and data should be protected.Inventory, locker status, user permissions, and configurations are protected from unauthorised modification.
DP-01Sensitive data should be protected.Patient information, prescriptions, and inventory are securely stored and protected from unauthorised access.
DP-03Input validation should guard against vulnerabilities.PIN entries, login credentials, medicine records, and user inputs are validated to prevent malicious data.
DP-04Access control mechanisms should prevent unauthorized data access.Role-based access ensures only doctors prescribe, nurses restock, and patients collect their own medicine.
AP-01Lock-out mechanism should protect against repeated unauthorized attempts.The locker temporarily locks after several incorrect PIN attempts and alerts staff.
AP-02Multi-factor authentication should be employed for impactful operations.Restocking and admin changes require RFID authentication plus administrator login.
AP-03Physical access restrictions should be implemented.The locker stays physically locked, unlocking only after a valid PIN is authenticated.
AP-05Proper session management should be employed.User sessions automatically end after collection or logout to prevent unauthorised reuse.
RS-01Device may support integrity of self-test and error detection.The system continuously monitors the DHT sensor, ultrasonic sensor, and servo motor for abnormal conditions.
RS-03Systems should withstand malicious attacks and resource exhaustion.The cloud server monitors requests and restricts excessive or abnormal access attempts.
RS-04Regular backup of system data should be conducted.Patient records, prescriptions, and inventory databases are regularly backed up for recovery.
Security audit — AU-01 · AU-02 · AU-03 The system also records significant security events — login attempts, medicine collection, RFID authentication, and inventory updates — with timestamps, protects audit logs from unauthorised modification, and encrypts logs to preserve confidentiality and integrity.
11 / Security Testing Plan

What we'll verify before calling it secure.

  • Temporary lockout is enforced after 3 incorrect authentication attempts.
  • A collection authentication method can be verified once, and only once.
  • ThingSpeak flags abnormalities, and the buzzer signals when the locker isn't closed properly.

12 / Conclusion

A secure end-to-end system, proven out.

MediSync is a secure edge-to-cloud IoT medication self-collection locker that combines user authentication, physical locker control, environmental monitoring, cloud visualization, role-based access control, and security-event logging.

The proof of concept demonstrates how the ESP32, sensors, actuators, a web application, MongoDB, and ThingSpeak can be integrated into a secure, end-to-end system — with security testing used to evaluate whether the implemented controls can prevent unauthorized access, data exposure, and reuse of collection credentials.
